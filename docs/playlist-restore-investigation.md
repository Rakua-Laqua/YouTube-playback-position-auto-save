# プレイリスト再生後の再起動で先頭の動画に戻る件の調査

記録開始: 2026-09-24

2026-09-27追記: 診断ログを `schemaVersion: 2` に拡張した。現在の記録項目・有効化手順・解釈上の制約は [ナビゲーション診断ログ](navigation-diagnostics.md) を参照する。以下の観察記録は旧ログによるものであり、URL一致や `loading` の記録だけから、文書全体の読み込みやURL変更の実行主体を断定しない。

## 症状

プレイリストを長時間再生した後にChromeを閉じて開き直すと、#6まで進んでいたのに#1の動画で復元されることがある。短時間の再生後に閉じた場合は、閉じる前の動画で正しく復元される。これとは別に、画面上では3番目に表示されている動画のURLが `index=4` になっている、というずれも観察されている。

## これまでに確認したこと

この拡張機能はURLを読むだけで書き換えない。`location.search` を読んでいるのは、動画IDの取得と `?t=` の有無の判定の2か所だけである。`history.pushState` / `replaceState`、`location` への代入、ページの再読み込みはどのファイルにもない。影響できるのは同じ動画の中での再生位置（`currentTime`）と一時的な消音に限られるため、どの動画を開くかは変えられない。

併用しているYouTube NonStop（v0.9.2、ID `nlkaejimjacpillmajjnopmpbkbnocid`）も、インストール済みのソースを読んだ範囲ではURLや履歴に触れていない。していることは、「続きを視聴しますか？」の確認画面を閉じること、操作していない間は `video.pause()` を実行しないこと、メディアキーの一時停止の処理を横取りすることの3つだけである。本拡張との関わりは、保存位置へ移動する前の一時停止（`pauseForRestore`）がNonStopに止められ、移動の直前に音が一瞬出ることがある点だけで、どの動画が開くかには影響しない。

YouTubeが開く動画を決めるのは `v=` であり、`index=` は補助的な情報である。そのため `index` がずれていても、別の動画が開くことはない。ずれの原因としては、プレイリスト内の削除済み・非公開の動画を、画面の番号は飛ばして数え、`index` は飛ばさずに数えていることが考えられる（確度は中程度）。

以上から、原因の候補はChromeのセッション復元とYouTube本体の2つに絞られる。短時間の再生では正しく復元されることから、長時間再生した後にだけ成り立つ条件が関係していると考えられる。例えば、PCのスリープ・シャットダウン・更新による再起動でChromeが強制終了されること、タブのクラッシュ、タブの破棄などである。いずれも現時点では確かめられていない。

### 短時間の再現手順（13:46〜13:47）

拡張機能を再読み込みして診断ログを有効にしたうえで、プレイリストを#1から開き、「次へ」で#3まで進めてから×ボタンで閉じ、開き直した。結果は#3で復元され、#1には戻らなかった。診断ログの記録は次のとおりである。

- #1（`tNgHm0yd3PE`）を開いた直後、URLは `index=1` から `index=2` に書き換わった。「次へ」で#2・#3に進んだときの `index` は2・3で正しかった。開き直した後、#3（`X1ThzQ1qnnI`）のURLは `index=3` から `index=4` に書き換わった。ページを丸ごと読み込んだときだけ、YouTube自身が `index` を1つ大きく付け直していることになる。どちらの拡張機能もURLを書き換えないので、これはYouTubeの挙動である。どの動画を開くかは `v=` で決まるため、このずれは害がない。
- 開き直したとき、Chromeは最初から#3のURLでタブを作っていた（`tab-created`）。

この手順では、Chromeのプロセスが実際には終了していなかった。根拠は2つある。1つ目に、`browser-startup` が記録されず、代わりに `tab-created` が記録された。`runtime.onStartup` はブラウザのプロセスが起動したときにしか発生しない。2つ目に、拡張機能のストレージ（LevelDB）は、ブラウザのプロセスが起動した後に初めて使われたときに開かれる。その記録（`LOG`）が13:33のまま更新されていなかった。つまり、試したのは「動いているChromeでウィンドウを閉じて開き直す」操作であり、9/24 11:20から9/25 13:33の間に起きた「プロセスが一度終了してからの起動」とは条件が違う。仮説はまだ否定されていない。

### 再起動による起動（13:52〜13:54）

プレイリストの#1から「次へ」で#3まで進め、PCを再起動した。今回は拡張機能のストレージが13:54:01に開き直され、`browser-startup` も記録されているので、Chromeのプロセスが実際に起動し直している。Chromeは起動した時点で#3（`X1ThzQ1qnnI`、`index=3`）のタブを作り、その後YouTubeが `index=4` に付け直した。#3で正しく復元された。

したがって、「最後にページを丸ごと読み込んだ動画に戻る」という仮説は、短時間の再生でPCを正常に再起動した場合には成り立たない。9/24に症状が出たときとの違いは、長時間の再生（1時間ほどで5本進んだ）と、Chromeがどう終了したか（不明）の2点である。どちらが原因かは、次に症状が出たときの `browser-startup` の記録で判断する。

症状が出た4件すべてで、戻り先は「ユーザーの操作で移った最後の動画」に一致する。そこから先に自動再生で進んだ分が失われている。

| 10/12→10/13 | #7（`ySklJV603QE`） | #1（`JmUnGlKrAb4`） | 再生リストのページからクリック | 約10〜13分おきに#2〜#7（自動再生） |

9/25 13:52 の検証では、「次へ」ボタンで#2・#3へ進んだ（どちらもユーザーの操作による移動）。この場合は#3に正しく戻っており、規則と矛盾しない。

Chrome は、ユーザーの操作なしにスクリプトが追加した履歴エントリを「戻る」ボタンで飛ばす（history manipulation intervention）。自動再生で次の動画へ進むときの `pushState` は、この「ユーザー操作なし」に当たる。復元でもこの区別が使われ、操作なしで追加されたエントリが飛ばされている、と考えるとすべての観察を説明できる。ただし、セッションファイルの各エントリに保存されている遷移の種類（`transition=0x0`）と `type_mask` には違いがなく、Chrome の内部で何が判断に使われているかは確認できていない（確度は中程度）。

## 対策（background.js の復元補正）

Chrome がタブを作った時点の URL は、webNavigation を記録できた2件とも正しかった。そこで、この URL を正しい復元先として扱う。検出する並びは次のとおりである。

1. `tabs.onCreated` で、未読み込み（`unloaded`）の `/watch` のタブが作られる。これは復元されたタブである。
2. 同じ URL の `onBeforeNavigate` が来る。
3. 同じ URL の `onErrorOccurred`（`net::ERR_ABORTED`）が来る。
4. 中断から1000ms以内に、別の URL の `onBeforeNavigate` が来る。
5. その URL の `onCommitted` が来たら、`chrome.tabs.update` で1の URL へ移動する。

並びから外れた時点で監視をやめる。正しく復元された場合も、確定した時点で監視が終わる。背面の復元タブは選択されるまで読み込まれず、その間に Service Worker が止まることがある。そのため、監視の状態は `chrome.storage.session` に置く。拡張機能の設定が無効のときは移動しない。補正したときは、診断ログに `restore-corrected` を残す。

この対策は Chrome の挙動を後から打ち消すもので、すり替えそのものは防げない。補正の前に#2が一瞬読み込まれる。戻る操作の履歴には、#2の後に#4が新しく積まれる。


## 診断ログ（初期形式）

`background.js` が、Chromeから見たYouTubeタブのURLを `chrome.storage.local` の `diag_nav_log` に記録する。Chromeのセッション復元が使うのはタブのURLなので、ページの中ではなくtabs APIから見た値を記録している。記録は最大500件で、古いものから消える。書き出しと削除は、ポップアップの設定画面にある「診断ログ（一時的）」から行う。

記録を始めるには、`chrome://extensions` でこの拡張機能を再読み込みする必要がある。2026-09-25に確認したところ、Chromeを再起動した後も診断ログは0件だった。一方で、再生位置の保存はその後も続いていた。ChromeのService Workerのスクリプトキャッシュ（`Default/Service Worker/ScriptCache`）にも2026-09-22の版しか残っていなかった。このことから、読み込み済み（パッケージ化されていない）拡張機能では、再起動だけでは新しい `background.js` に切り替わらないと考えられる。ポップアップとコンテンツスクリプトは再起動後に新しい版が使われるので、ボタンが表示されていても記録が始まっているとは限らない。

| event | 記録するタイミング | 主な項目 |
| --- | --- | --- |
| `browser-startup` | Chrome起動時 | その時点のYouTubeタブ一覧（`url` または `pendingUrl`、`status`、`discarded`） |
| `extension-install` / `extension-update` | 拡張機能のインストール・更新・再読み込み | 同上 |
| `tab-created` | YouTubeのタブが開いたとき | タブのURL |
| `tab-updated` | URLの変化（プレイリストの次の動画への移動を含む）、読み込みの開始、タブの破棄 | `urlChanged`、`status`、`discarded`、`parsed.v` / `list` / `index` |

タブを閉じたとき（`tabs.onRemoved`）は記録しない。Chromeが終了するときはService Workerの書き込みが完了する保証がないため、記録があるかどうかから終了の仕方を判断できないからである。

## ログの読み方

症状が出たら、再起動の直後にログを書き出し、最後の `browser-startup` とその直前の記録を比べる。

- 起動直前の最後の `tab-updated` が#6なのに、`browser-startup` のタブが#1を指している場合は、Chromeが古いURLを復元している。閉じ方（強制終了されたかどうか）を確かめる。
- 起動直前の最後の `tab-updated` がすでに#1を指している場合は、閉じる前の時点でYouTube側が#1に移動していた。その直前の記録から、いつ移動したかを追う。
- `browser-startup` のタブが#6で、その後の `tab-updated` で#1に変わっている場合は、YouTubeが読み込み後に移動させている。

ログでは分からないことが2つあるため、症状が出たときに手元で控えておく。1つはChromeの閉じ方（×ボタンか、PCのシャットダウンやスリープか）、もう1つは起動時に「ページを復元しますか？」が表示されたかどうかである。

## 片付け

原因が分かったら、診断ログの機能（`background.js` の診断ログの部分、ポップアップの「診断ログ（一時的）」、`shared.js` の `DIAG_LOG_KEY` / `appendDiagEntry` / `parseWatchUrl`、関連するテストと翻訳文字列）を取り除き、このメモに結論を書き足す。
